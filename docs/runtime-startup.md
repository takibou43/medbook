# الإقلاع وترحيلات قاعدة البيانات

`npm start` وDocker يشغّلان التطبيق فقط. لا ينفّذ أي منهما `db push` أو SQL أو
ترحيلات تلقائية. توليد Prisma Client والبناء يظلان في مرحلة البناء.

## قاعدة Docker جديدة

بعد ضبط كلمات المرور والأسرار محليًا:

```sh
docker compose build
docker compose up -d postgres
docker compose run --rm backend npm run db:bootstrap:local
docker compose up -d
```

التهيئة عملية مقصودة لمرة واحدة. تقبل PostgreSQL على loopback أو اسم خدمة
Compose `postgres`، واسم القاعدة `medbook`، والمخطط `public` فقط. ترفض قاعدة
تحوي جداول أو سجل ترحيلات، ولا تمسح أو تعيد إنشاء أي بيانات. تستخدم نسخة مؤقتة
من مرشح الترحيلات الذي يعاد اختباره في CI؛ لا تنقل سجل الإنتاج إلى هذا المرشح.
إذا انقطعت التهيئة، راجع سبب الخطأ وحالة الترحيلات؛ لا تحذف وحدة التخزين لإصلاحه.

لإعادة تشغيل قاعدة محلية قائمة، يكفي `docker compose up -d` دون التهيئة.

## الإنتاج

هذا التغيير يفصل الإقلاع عن تغيير المخطط فقط: لا يغيّر المخطط ولا يتبنى baseline
ولا يطبّق حراسات ناقصة على الإنتاج. لا توجد تغييرات مخطط في هذا الإصدار.

قبل النشر، تحقق من أمر Render الفعلي: يجب أن يستعمل `npm start` بعد البناء؛
أي `prisma db push` مكتوب مباشرة في إعداد المنصة يحتاج الإزالة ضمن النشر نفسه.
تحقق من نسخة احتياطية قابلة للاستعادة وتوافق المخطط الحالي مع النسخة المنشورة.

عند إضافة تغيير مخطط مستقبلًا، نفّذ الترحيل المراجع صراحةً قبل تشغيل التطبيق.
يبقى الانتقال إلى سجل baseline عملًا مستقلًا خاضعًا لحواجز
`prisma/migration-candidate/README.md` وطلب الدمج القائم #139. لا تشغّل
`prisma:deploy` القديم على الإنتاج دون حسم سجل الترحيلات، ولا تستعمل
`db:bootstrap:local` معه. لا fallback إلى `db push` عند الفشل.

الرجوع يكون إلى إصدار تطبيق متوافق مع المخطط، مع أمر تشغيل بلا كتابة للمخطط؛
إرجاع أمر `db push` القديم ليس خطة استعادة.
