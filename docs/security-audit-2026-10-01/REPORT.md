## Neon: الوضع الفعلي لـRLS والصلاحيات

المشروع المقروء: calm-lake-84943874، باسم medbook. الفرع الإنتاجي الافتراضي: br-bitter-mouse-a5fk66jy. قاعدة neondb. إصدار PostgreSQL المقروء: 18.6.

الكتالوج الفعلي أظهر 35 جدولًا عامًا، جميعها RLS غير مفعلة وFORCE RLS غير مفعلة، وصفر policies. المالك neondb_owner. هذا الدور ليس superuser لكنه يملك BYPASSRLS وعضوية neon_superuser. لا يكفي FORCE RLS لمنع دور يحمل BYPASSRLS من التجاوز؛ مرجع PostgreSQL: https://www.postgresql.org/docs/17/ddl-rowsecurity.html

مهم: اتصال أداة Neon قرأ البيانات كـneondb_owner؛ هذا لا يثبت أن DATABASE_URL المستخدمة داخل Render تتصل بالدور نفسه. لم يُتحقق من دور Prisma الفعلي للإنتاج. الملف inspect-prisma-role.cjs جاهز لقراءة current_user وخصائص الدور والكتالوج في معاملة READ ONLY من بيئة التطبيق، دون طباعة رابط الاتصال أو كلمة المرور. يجب تشغيله في البيئة المقصودة قبل تقرير أن Prisma تتجاوز RLS.

لم تظهر grants عامة للبيانات في الجداول المهمة؛ الصلاحيات المقروءة كانت للمالك. غياب RLS وحده ليس إثباتًا لوصول مجهول إلى قاعدة البيانات؛ التفويض على مستوى الخادم هو حاجز التطبيق الحالي.

تحققت القراءة من قيود الفريدة للحجز الفعال وidempotencyKey، تكرار رسائل العميل، endpoint أجهزة Push والحظر الفعال، ومن مفاتيح أجنبية ومشغلي appointments_sync_active_slot وappointments_release_dental_follow_up. اختبار DB المحلي استخدم schema push وثلاث migrations للحواجز: release_cancelled_slots وadd_review_guards وfamily_treatment_referrals_stats. لم يُعتمد تشغيل سلسلة migrations كاملة من الصفر.

لم يُعثر على Data API للفرع/القاعدة المقصودين في الطلب المستخدم (404). إعدادات المشروع تسمح باتصالات عامة ولا تظهر قائمة IP مقيدة؛ هذا تحسين دفاعي محتمل ولا يثبت اتصالًا مجهولًا أو تسرب بيانات. إعداد pooler المقروء غير مفعل، مع وضع transaction واسم مضيف pooled متاح؛ طريقة اتصال التطبيق الفعلية غير متحققة.

## تجربة RLS المعزولة والتوصية

اختُبرت سياسات على جدولَي notifications وpush subscriptions محليًا فقط. الملفات: rls-pilot.sql وrls-pilot-rollback.sql وrun-rls-pilot.cjs وrls-results.json. البرامج ترفض التشغيل على اسم قاعدة غير medbook_rls_test.

أُنشئ دور runtime محدود دون superuser أو BYPASSRLS ودور worker منفصل. فُعّلت ENABLE وFORCE RLS. الهوية transaction-local عبر set_config داخل معاملة Prisma مع التحقق من أن المستخدم نشط. غياب الهوية يرفض الوصول؛ المريض والطبيب والمساعد والمدير يرون إشعاراتهم فقط. تحديث إشعار يقتصر على isRead، ولا يستطيع runtime إنشاء إشعارات نظام. سياسات Push تمنع قراءة/حذف جهاز الغير ونقل ملكيته؛ worker يملك الحد اللازم للإرسال وإنشاء الإشعارات وحذف المنتهي. 80 معاملة عبر اتصالين لم تسرب الهوية، واختُبر rollback دون حذف السجلات.

هذه تجربة ناجحة وليست حماية RLS مكتملة للمشروع. لا تُطبق SQL على الإنتاج كما هي. يلزم دور migrations مالك منفصل، ودور runtime محدود، وتمرير transaction client في الخدمات، وسياسات المواعيد والرسائل والعائلة ومالك العيادة والوظائف الخلفية والتتبع العام. كذلك يمنع pilot انتقال ملكية Push الذي قد تستعمله آلية تسجيل الجهاز الحالية؛ يجب تصميم عملية موثوقة لهذا التدفق قبل التطبيق. اختبار pool المحلي لا يثبت توافق Neon PgBouncer. يلزم اختبار الفرع السحابي المعزول وخطة رجوع وموافقة النشر.
